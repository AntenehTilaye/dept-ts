=== CAMPAIGN ENGINE
 One engine, one vocabulary, kind adapters as presets, one lifecycle implementation. === NOTIFICATION/SCHEDULING
 The Scheduler & Notification service is the only path to deferred work and to inboxes; no module calls the job runner, email or SMS directly. Deadlines are declared once as ReminderSubscriptions bound to a subject and either an absolute datetime or a calendar anchor {periodKind, edge, offsetDays, termId} resolved by the Academic Registry; a named ReminderSchedule (default -7d, -3d, -1d, 0, +1d overdue with channels per offset and optional escalation to a role after N overdue days) is materialised into ScheduledJobs with unique idempotency keys '{subjectRef}:{scheduleKey}:{offset}', skipping past offsets. Recurring tasks and meeting series use RecurrenceRule with recurrence_spawn. === RBAC
 Three layers evaluated by one function, Identity.can(actor, permissionKey, subjectRef). (1) Roles bundle permission keys named module.action with a level, seeded from the section 30 matrix as RolePermission data (Committees: DH full, DPT full, Instructor assigned, CommitteeMember assigned, CommitteeChair assigned plus committee.task.manage and committee.report.submit; Tasks: full/full/assigned/assigned/limited for reps; Portfolio: review/review/own; Evaluation: full/manage/own/participate; Add/Drop and Electives: full/manage/submit; Staff Profiles: full/manage/own; Resources: full/manage/view; Meetings: full/full/participate/participate/limited; Lab: LAB_STAFF lab.task.manage assigned scoped to lab_schedule) and editable by the System Administrator with 'simulate as user'; DPT defaults to the DH set minus a SystemSetting-held exclusion list (portfolio approve, evaluation.close, evaluation.analyze, plan.approve, minutes.approve), expressible because campaign transitions use kind-specific keys. Level semantics are defined in the policy decision point: full = any action in scope; manage = all but the excluded approvals; review = read plus review/approve transitions where the actor satisfies the reviewer rule; own = owner relationship; assigned = assignee (including via group or adhoc audience group) or member/chair of the subject's context group; participate = target or invited participant (campaign invitation holder, meeting participant, evaluation respondent); limited = read and comment only where relationships include requester (Case.requesterPersonId for a rep's escalated issue), participant of a meeting whose minutes are approved, or representative of the section the task's context or Case.sectionId points to; view = read within scope; submit = create and edit own submissions only. (2) Scoped grants: RoleGrant carries scopeType/scopeId (global, department, committee, section, program, section_offering, lab_schedule, meeting) and validity; most non-leadership access is derived from registry facts by outbox handlers and repaired by a nightly idempotent grant_reconcile job: GroupMembership(kind=committee) -> COMMITTEE_MEMBER@committee and, for roleInGroup=chair, COMMITTEE_CHAIR@committee; SectionRepresentative -> STUDENT_REP@section plus Identity.inviteUser when no User exists; TeachingAssignment -> INSTRUCTOR@section_offering; lab DutyAssignment -> LAB_STAFF@lab_schedule; StudentSectionMembership -> STUDENT@section; Group.status inactive expires the commit

=== INTEGRATION
 Excel/CSV assessment import: instructors download a template pre-filled from the Enrollment roster and the offering's AssessmentScheme columns, then create an ImportBatch(kind=assessment, contextRef=section_offering) by file upload or manual grid. The batch is parsed, columns mapped (saved ColumnMappingProfile with header aliases), validated against roster and scheme (unknown or duplicate student IDs, fuzzy name mismatch warnings, marks outside 0..maxMark, non-numeric values, missing components, missing roster students, total recomputation), previewed with row-level fixes, and committed atomically: AssessmentRecords for the section offering are replaced per batch, StudentCourseResult and CourseMetricsSnapshot are recomputed by snapshot_compute (which also recomputes the open CQIReport comparison), the original file is retained as the batch's source Document, and every record carries importBatchId. Commit is refused by the import.sectionNotLocked guard once that SectionOffering has been locked by its portfolio's approval; other sections of the same offering remain open, and the offering-level scheme structure locks only when all taught sections are locked or the offering completes. Attendance (optional per_student mode) uses the same pipeline with kind=attendance producing StudentAttendanceSummary rows; the default aggregate mode records attendance in the portfolio narrative. Load-assignment integration (section 14): the preference campaign closes and seeds ReviewedPreference rows for the term's LoadCycle; the department reviews (accept, adjust, reject, add) with comments; export applies the active ExportFormatSpec (targetSystem load_assigner, rowSource reviewed_preferences) validated against a stored golden sample, producing an Excel Document and a LoadExport record with spec version and source hash; the assigner's output returns through ImportBatch(kind=load_result) with its own mapping profile, is diffed against existing TeachingAssignments in a review step and applied as TeachingAssignment rows with source=load_import, which drive portfolio provisioning, evaluation subjects, workload and derived INSTRUCTOR grants. Format drift in either direction is absorbed by editing the spec or the mapping profile. Lab schedule import (section 19): the school's file becomes an ImportBatch(kind=lab_schedule) validated by a context provider resolving labs to Resources and courses/sections to SectionOfferings and checking overlapping slots; committing creates LabSessions with source=import; the department then creates DutyAssignments (lab_instructor, ra, responsible) and publishes the LabSchedule through schedule_publication. Class timetable import (kind=class_timetable) and optional exam timetable import (kind=exam_timetable) use the same pipeline. Invigilation and lab conflict detection: every time claim (ClassTimetableSlot, LabSession, DutyAssignment, ExamSession, Meeting, confirmed Appointment, AvailabilityPolicy blackouts) is projected by outbox handlers

=== RISKS
- Assessment uploads with wrong headers, unknown students, out-of-range marks, duplicates or missing students corrupt records.
    -> All uploads pass through the Tabular Import pipeline with roster-prefilled templates, saved mappings, validation, row-level fixes, atomic per-section commit replacing the previous batch, per-section lock on portfolio approval, snapshot recompute event and field-level audit.
- One approved portfolio blocks other instructors of a multi-section course from uploading or fixing marks.
    -> Assessment locks are per SectionOffering (set only for the approved portfolio's scopes); the offering-level scheme structure locks only when all taught sections are locked or the offering completes; the import guard reads the section lock.
- The external load-assignment system changes its Excel layout in either direction.
    -> Versioned admin-editable ExportFormatSpecs with golden-sample validation and recorded spec version/source hash; return path through an ImportBatch with its own mapping profile and diff review.
- Invigilation and lab duties double-book people or rooms, or the hard exclusion constraint rejects legitimate meetings and appointments.
    -> One AvailabilityBlock ledger with explicit severity: resource and duty/teaching/leave blocks are hard and constraint-enforced; meeting attendee and appointment requester blocks are soft and advisory; guards check hard conflicts only; boards show both.
- Quarterly reports drift from actual progress or lose the narrative on regeneration.
    -> PlannedActivity classification derives from workflow state and dates; regeneration replaces only the computed snapshot; each render is a new DocumentVersion; Waived state covers skipped quarters.
- Generated minutes diverge from meeting data or approvals are untraceable.
    -> Structured meeting data, guarded generate transition, ten-section template, versioned Document, approval recorded once in the transition log payload with the approved version locked.
- Calendar-driven reminders fire late, twice or against stale dates.
    -> Anchored subscriptions re-resolved on period change, idempotency and dedupe keys, staleness rule, impact preview and dry-run, mass-send confirmation.
- Anonymous evaluations are de-anonymisable.
    -> No foreign-key path between invitation and submission, separate writes, day-truncated timestamps, coarse cohort attributes, k-anonymity per cell, free-text policy, actor-less audit rows, DH-only close/analyze keys, adversarial query tests before Phase 4.
- The suite degrades into independent CRUD modules with parallel mechanisms (section 33).
    -> Review rules: lifecycle state with transitions only in WorkflowInstance with enumerated attribute flags; timestamps on subject rows are derived caches written by workflow effects; one acknowledgement/decline mechanism (Notification); one deliverable source (DocumentLink); one duty table (DutyAssignm
- Inner-platform effect: generic engines slow simple features and invite misconfiguration.
    -> Definitions ship as code-defined presets; admin editing limited to guarded fields; guards are registered functions; simulate/preview tools; instances pin definition versions with audited migrations.
- Polymorphic SubjectRef references lose referential integrity.
    -> SubjectRegistry enforces existence on write and cascades on delete; indexed (subjectType, subjectId); labels denormalised; reporting via per-type read models.
- Historical CQI comparison has no baseline.
    -> Course lineage, immutable snapshots, comparison strategies with fallbacks and explicit 'no data' rows; CQIReport created at provision so the instructor sees baselines from day one.
- Derived scoped grants become stale.
    -> Derived grants carry derivedFromRef; event handlers plus nightly reconciliation; live relationship checks; audit; deny by default.
- Cohort history rewritten when students progress or repeat.
    -> Time-varying StudentSectionMembership and SectionRepresentative; cohort attributes copied at submit time.
- Students, representatives and external stakeholders lack accounts.
    -> Representatives are auto-invited when assigned; notifications deliver by email to persons without a User; tokens and request links work without login; logins later only add User rows and derived grants.
- Dashboards slow down as data accumulates.
    -> Event-maintained projections with rebuild commands, materialised snapshots, partitioned audit, archivable closed years.
- Stack, auth provider and channels undecided in parallel with kernel build.
    -> Adapter interfaces for authentication, job runner, object storage, channel senders and renderers fixed in Phase 0.
