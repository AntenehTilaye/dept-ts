=== OVERVIEW
 The Department Management Tool Suite is a Department Operating System: a platform kernel of reusable services plus thin feature modules that are mostly configuration, adapters and a few module-specific tables. The kernel has three layers. The foundation layer is a canonical registry every feature row references by foreign key: Identity & Access (roles, permissions, scoped grants derived from registry facts), People & Org (Department, one Person record, StaffProfile, Student with time-varying StudentSectionMembership and SectionRepresentative, the reusable Group abstraction, audience resolution) and the Academic Registry & Calendar (AcademicYear with quarter boundaries, Term, typed CalendarPeriod, Program, cohort Section, Course with lineage, CourseOffering, SectionOffering, one TeachingAssignment table, Enrollment, ClassTimetableSlot and a single Resource table for rooms and labs). The engine layer is the set of polymorphic services that own behaviour no module may re-implement: Work Item (one Task table for individual, committee, department, meeting action items, cases, planned activities, CQI actions, lab and maintenance tasks), Workflow Engine (data-defined state machines that own every lifecycle state that has transitions; lifecycle timestamps on subject rows are derived caches written only by workflow effects), Form/Campaign Engine (versioned FormDefinitions run either as windowed Campaigns or as standalone Submissions bound to a workflow, so committee reports, portfolio narratives, CQI narratives, quarterly narratives and appointment requests reuse the same question/answer machinery as evaluations, add/drop, electives and preferences), Scheduler & Notification (calendar-anchored reminder subscriptions, idempotent jobs, per-user inbox that is the single acknowledgement and decline mechanism for tasks, duties and announcements), Template & Rendering, Document (immutable versions, polymorphic links, inherited access; the only place files and deliverables live), Comment/Thread (task comments, revision notes, case notes and DH-to-rep conversations), Audit & Domain Events (transactional outbox), Tabular Import (staged parse/map/validate/preview/commit pipeline shared by assessment, attendance, lab schedule, timetable, load results and rosters), Availability & Conflict (one AvailabilityBlock ledger with hard and soft severities for persons and resources), Reporting & Export (registered report definitions plus admin-editable, versioned ExportFormatSpecs for external systems), Search (ACL-filtered projection) and a Dashboard read-model service that owns cross-module projections such as open issues and staff activity. The glue is the SubjectRegistry contract: every module registers, per subject type, how to label, snapshot, contextualise, expose relationships, template variables, search documents and access resolution, so every kernel service references any entity through one SubjectRef vocabulary. Feature modules are adapters: a committee is a Group plus Tasks plus a committee_report form submission under a workflow; an annual activity and a case are Task extensions; evaluations, add/drop, electives, preferences and surveys are Campaign kind adapters; minutes and quarterly reports are Templates rendered into versioned Documents; invigilation and lab staffing share one DutyAssignment table under term-level schedule_publication workflows with acknowledgement and decline tracked on Notifications. Section 14 has an explicit ReviewedPreference review layer feeding a versioned ExportFormatSpec, and the return path uses the import pipeline to write TeachingAssignment rows. Anonymity in evaluations is structural (no foreign-key path between invitation and submission, day-truncated timestamps, coarse cohort attributes, k-anonymity gate). Delivery is kernel-first (Phase 0 kernel and registry including the availability, thread and leave seams; Phase 1 DH cockpit; Phase 2 identified campaigns, load bridge and planning; Phase 3 assessment/portfolio/CQI; Phase 4 anonymous evaluations and conflict-heavy scheduling; Phase 5 resources, search, analytics, hardening). Review rules keep the design from decaying into independent CRUD modules: lifecycle state with transitions lives only in WorkflowInstance (simple attribute flags such as Resource.status or Enrollment.status are permitted and enumerated), no direct file storage, jobs or email calls, any task-like thing is a Task extension, any collection is a Campaign kind or standalone form, any note is a Thread comment, any time claim is an AvailabilityBlock, any acknowledgement or decline is a Notification ack, any cross-module count is a Dashboard projection.
