# Deviations from the design documents

The code is authoritative; this file records where and why it departs from `03`–`07`.

| Phase | Design said | Implementation | Why |
| --- | --- | --- | --- |
| P0 | `eslint@10` | `eslint@9.39.5` | `eslint-config-next@16.3.5` bundles an `eslint-plugin-react` that still calls `context.getFilename`, which ESLint 10 removed. `create-next-app` pins 9 for the same reason. |
| P0 | `vite-tsconfig-paths` plugin in `vitest.config.ts` | `resolve.tsconfigPaths: true` | Vite 8 resolves tsconfig paths natively and warns about the plugin. |
| P0 | `cn` npm package | `src/lib/utils.ts` (`clsx` + `tailwind-merge`) | Same helper, one fewer dependency. |
| P0 | `GRANT CREATE ON DATABASE dept_test TO dept_app` only | granted on `dept`, `dept_test` and `dept_e2e` | pg-boss (`migrate: true`, running as `dept_app`) issues `CREATE SCHEMA IF NOT EXISTS pgboss`; PostgreSQL checks the database CREATE privilege before the existence check. |
| P0 | — | `ENV DATABASE_URL_MIGRATE=postgresql://build:build@db:5432/dept` in the Docker build stages | `prisma.config.ts` resolves the variable with `env()` at load time, which `prisma generate` (postinstall) needs even though it never connects. Runtime environments override it. |
| P0 | Playwright HTML report under `tests/e2e/.results/html` | `tests/e2e/.report` | Playwright refuses an HTML report folder inside `outputDir`. |
| P0 | `@prisma/internals` `getDMMF` named import | default import, then destructure | The package is CommonJS; Node's ESM loader cannot see `getDMMF` as a named export. |
| P2 | Departments created through `auth.api.createOrganization` with a compensating department row | `departmentService.create` writes the `organization` and `department` rows in one Prisma transaction | The plugin endpoint adds the caller as a member with `creatorRole`, which a faculty administrator must not become, and it cannot run inside the same transaction as the department row. The organization table is exactly what the plugin reads afterwards. |
| P2 | `requireDeptContext` calls `setActiveOrganization` on every request | The department comes from the URL slug; `selectDepartmentAction` records `activeOrganizationId` once (administrators who are not members get the session row updated directly because the plugin endpoint refuses non-members) | Setting cookies during a server-component render is not allowed in Next 16, and the slug already identifies the department unambiguously. |
| P2 | `/set-password/[token]` and `/reset-password/[token]` segments | `/set-password?token=` and `/reset-password?token=` | better-auth's reset endpoint redirects to `callbackURL?token=…`; the query form needs no rewrite. |
| P2 | better-auth rate limiting always on in production | `rateLimit.enabled` follows `AUTH_RATE_LIMIT` (default on in production builds; `compose.e2e.yaml` sets `0`) | The Playwright setup project signs seven seeded users in from one IP, which exceeds the built-in 3-per-10-seconds rule on `/sign-in/email`. |
| P2 | Coverage measured on integration + worker only | `npm run test:coverage` runs all four Vitest projects in the `test` service | `can()` and the matrix are covered by unit tests; the 85 % identity threshold only holds when unit coverage is merged in. |
| P3 | Registry pages under `/admin/{calendar,programs,courses,offerings,resources}` (phase detail) | Department pages `/d/[dept]/{calendar,programs,courses,offerings,resources,people,sections}` gated by `academic.manage` / `staff.view` (as the plan's P3 entry says) | The registry is department data edited by the head and deputy, not faculty administration; the multi-department layout keeps every tenant page under the department segment. |
| P3 | SubjectRegistry methods take only the subject id | Every registration method takes the caller's `Db` client first (`label(db, id)`, `contextOf(db, id)`, ...); `can()` gets a department-scoped client through `resolverWith(getDb)` | Registrations must read under the caller's RLS context (its department transaction) instead of opening their own connections; `can()` passes the actor's department so scoped lookups see the rows. |
| P3 | `person_full_name_trgm` created only by the hand-written migration | Also declared on the Person model (`@@index([fullName(ops: raw("gin_trgm_ops"))], type: Gin)`); the migration qualifies the opclass as `public.gin_trgm_ops` | `prisma migrate dev` diffs unknown non-partial indexes away (it dropped this one once); declaring it makes Prisma own it. Per-run test schemas do not have `public` on the migration search path, hence the qualified name in SQL. |
| P3 | Department-scoped client wraps model operations | Raw queries (`$queryRaw`, `$executeRaw`, unsafe variants) are wrapped too | The directory search uses pg_trgm SQL; without the wrapper it ran outside the department setting and RLS returned nothing. |
| P3 | e2e reset truncates non-seed tables | Also deletes users whose email is not in `SEED_USERS` | Invited representatives and admin-created accounts from a previous run made "new user" flows skip the invite mail. |
| P3 | `setPeriod` bounds a period by its term | Bounded by the academic year (up to 60 days before its start) | Registration and course-preference windows precede the term they belong to. |
| P4 | `purge_domain_events` is `SECURITY DEFINER` with a fixed search path | Plain function executed by the worker under tenant bypass | A fixed `search_path` would point per-run test schemas at `public.domain_event`; bypass already lifts RLS for the retention job. |
| P4 | Audit and outbox rows always carry the caller's department | Faculty-level rows (`department_id IS NULL`) may be inserted without bypass through an extra permissive `faculty_insert` policy on `audit_event` and `domain_event` | Global-table writes from admin pages and provisioning have no department and must still be audited. |
| P4 | Audit interceptor writes on "the caller's transaction" | The transaction, actor and correlation id travel in an AsyncLocalStorage context (`src/platform/audit/context.ts`) set by `withTenantTx`, `withTenantBypass`, the scoped client and the action wrappers; every wrapper awaits inside the scope | Prisma query extensions cannot reach the enclosing interactive transaction; lazily executed Prisma promises only keep the context when awaited inside it. |
| P4 | Module-level registries and caches | Registries, caches and the audit AsyncLocalStorage live on `globalThis` (`src/lib/singleton.ts`) | Next.js instantiates shared modules once per route chunk, so a module-level `Map` in the interceptor's chunk differed from the one the action wrapper wrote to (the audit actor arrived as "system" in the production build). |
| P4 | Organization hooks call derive directly | Hooks publish `member.changed` / `member.removed`; the grants subscriber derives | As designed for P4; the people/academic services still derive synchronously for immediate consistency and the subscribers repair drift. |
| P5 | `email.send` before `email.dead` in the queue catalogue | `email.dead` is declared first | pg-boss validates that a `deadLetter` queue exists when the referencing queue is created. |
| P5 | Notifications render their template at delivery time | `Notification.renderedJson` stores the email/sms variants rendered by `notify()`; the delivery reuses them (re-render only for rows without it) | The variables (subject label, deadline, days) exist only at notify time; re-rendering later produced empty placeholders. |
| P5 | Offset 0 counts as overdue | Offset 0 is the deadline-day reminder (`deadline_reminder`, category `deadline_approaching`); only positive offsets are overdue | Matches the seeded schedules, whose offset-0 entry uses the reminder template. |
| P5 | Integration project runs without pg-boss | `tests/setup/global-boss.ts` migrates a per-run `pgboss_it_<run>` schema for both database projects | `notify()` enqueues email deliveries and `subscribeReminders` enqueues `reminder.fire` on the caller's transaction, so integration tests need a queue schema even without a supervising worker. |
| P5 | `/admin/reminders` dry run only | Also a "fire a test reminder now" action (department-head audience, deadline in 2 s) | Gives administrators and the e2e suite an end-to-end check of schedule → ledger → worker → template → mail without waiting for a real deadline. |
| P5 | Confirm `APP_TIMEZONE` with the user before the phase | Kept the P0 default `Africa/Addis_Ababa` (overridable through the environment) | The user asked to proceed without questions; the value is a one-line environment change. |
| UI | Plain server-rendered forms and tables per module page | Application shell (collapsible sidebar, mobile sheet, command palette, theme toggle, inbox bell, user menu) plus the pattern layer in `docs/design/08-ui-standard.md`; official shadcn/ui components generated by the CLI | The user asked for researched best-practice UI/UX and shadcn; the standard is now the bar for every later phase. |
| UI | `CardTitle` is a `div` in upstream shadcn | Renders an `h2` | Card sections must be reachable by heading navigation (WCAG 1.3.1/2.4.6) and the e2e suite addresses them as headings. |
| UI | Page-level `notFound()` returns HTTP 404 | With the route `loading.tsx` boundaries a page-level `notFound()` renders the 404 page with status 200 (the layout still answers a real 404 to non-members) | The response is already streaming when the page decides; the skeleton on navigation is worth more than the status code for an authenticated app. |
| UI | Notification email preferences submit the categories switched off | The form submits the categories that are on (`emailOn`); off rows are derived | A switch labelled with the category reads "email on/off" naturally; the stored representation is unchanged. |
| P6 | `document_version_lock()`/`document_version_purge()` as SECURITY DEFINER with a fixed search path | SECURITY DEFINER without `SET search_path`; the lock function repeats the tenant check (`app.current_department_id` or bypass), the purge function requires bypass | The migrator-owned definer must bypass the column REVOKEs, but a fixed `search_path` would point per-run test schemas at `public` (P4 lesson); the explicit checks replace what RLS would have done. |
| P6 | Comment and upload rights through dedicated permission keys | Contributing (upload, link, post) is `document.manage` on the subject or an *involvement* relationship (owner, creator, assignee, member, chair, participant, requester, reviewer, section representative); thread reading follows the same rule; reading documents uses `document.read` on any linked subject | One level per role and key cannot express "owner OR assignee" (instructors need both: their profile and their tasks), and the §30 matrix has no comment keys; involvement is what the registry already exposes. |
| P6 | Rate limiter only for unauthenticated uploads | Per-address bucket (30 burst, 0.5/s) before the body is read plus a per-user bucket (60 burst, 1/s) | The address bucket also protects the body parser from anonymous abuse; a signed-in user is limited separately. |
| P6 | Signed link carries `documentId`, `versionNo`, `exp` | Also `departmentId` and the issuing `userId`; the download route requires the same session | The route must open the right tenant transaction without an RLS-blind lookup, and a link must not be forwardable. |
| P6 | `upload.maxBytes` read at `SystemSetting`, fallback `UPLOAD_MAX_MB` | As designed, plus `document.retentionDays` (default 90) for the purge provider | — |
| P6 | Text extraction for text/csv | Also markdown; PDF/DOCX remain for P27 | — |
| P7 | `PlannedActivity` created together with the other Task extensions | Only `Case` is created now; `PlannedActivity` arrives with the annual-plan phase | Its `annualPlanId` foreign key points at a table that does not exist yet (planning.prisma is a placeholder until P20). |
| P7 | The provisional `task` definition is registered by the seed | As designed, plus the `assigned.start` transition is applied **by the acknowledging assignee**, not as a system transition | A system transition cannot be applied by a person, and a null actor fails the actor rules; acknowledging one's own assignment is the honest actor anyway. |
| P7 | Recipients of a workflow `notify` effect come from the args | Services register named recipient rules (`registerRecipientRule`), and the work item registers `task_assignees` and `task_creator`; `actionUrlRule: "subject"` resolves the record URL through the SubjectRegistry | A definition cannot name people the scheduler knows nothing about, and hard-coding task lookups into the scheduler would invert the dependency. |
| P7 | The `notify` effect's `dedupe` argument is the whole key | It is scoped to the subject (`<subjectType>:<subjectId>:<dedupe>`) | A literal key in a definition would otherwise collide across every record of that feature. |
| P7 | `createTask` recorded as a no-op effect (P4) | Replaced by the real effect; the P4 test asserts the spawned task instead | As planned for this phase. |
| P7 | Recurrence spawns are scanned with the root client | The scan runs per department inside a department transaction | `recurrence_rule` is a tenant table, so the root client (NOBYPASSRLS, no department setting) sees nothing. |
| P7 | The ledger claim inserts and catches the unique violation | `createMany({ skipDuplicates: true })` (ON CONFLICT DO NOTHING) | A unique-violation error aborts the surrounding Postgres transaction, so the caller could not continue with the other due rules. |
| P7 | Page permission checks call `pageContextCan(dept, key)` | The task pages check `task.view` **against the task** (detail) and scope rows by whether a department-wide `task.view` exists (list) | Relationship levels (`assigned`, `own`) can only be resolved against a subject; a blanket check denies every assignee. |
| P7 | — (found in this phase) | The effect recorders of P4 now register only when a kind has no handler, and the `setField` allow-list lives on `globalThis` | Next.js loads a second copy of `workflow/effects.ts` in the production build; its module-scope registrations silently replaced the real `notify` handler and the module-local allow-list lost the task entry. |
| P7 | The seed exits after `runSeed` | It also stops the lazily started pg-boss client | The demo task seeder enqueues jobs, and the open pool otherwise keeps `prisma db seed` running forever. |
| P8 | `src/platform/campaign/{invitations,participation,anonymity,export,kinds/survey}.ts` | `service.ts` (create, publish, open, close, reschedule, `openLink`, `submitViaToken`, `participation`), `tokens.ts`, the pure `aggregation.ts` and `results.ts` (aggregate, read, export) | Anonymity is not a module: it is the database trigger plus the two branches of `submitViaToken`. Publishing resolves the audience, writes the invitations and enqueues the window jobs in one transaction, which one file per verb would have spread over five modules. |
| P8 | Results export as csv and xlsx | csv only (papaparse), stored through `document.storeGenerated` | xlsx belongs with the hardened export specs of P26; nothing in this phase reads it. |
| P8 | One component per question type plus `DraftAutosave`, `RankedList` and `RepeatingGroup` | A single `FormRenderer.tsx` renders every type including ranked lists and repeating groups; `saveDraft` exists as a service function but no screen autosaves yet | The answer shape (conditional visibility, group indices, rank order) is one concern; splitting it across components duplicated it. The public form is short enough that a lost draft costs a minute. |
| P8 | `/admin/forms/[key]` with a drag-ordered question editor | `/admin/forms/[formId]` with a JSON editor over the same `FieldDef` contract, a live preview and the version badges | The visual question builder is the feature wizard (P9–P11) and will read the same contract; keying the route on the version id makes every version addressable, including retired ones. |
| P8 | The admin form pages read the definitions with the root client | They read under an audited `withTenantBypass`, and saving a version keeps the form's department scope (hidden `departmentId`) | `form_definition` is SHARED, so department overrides are invisible to an admin session that has no department, and a version saved at faculty scope would fork the key instead of continuing the override. |
| P8 | `/c/[token]` looks the invitation up and opens it | `departmentOfToken` resolves the department under an audited bypass first, then the token is opened inside that department's transaction | `campaign_invitation` is tenant-scoped and the public route has no session: a plain lookup returns nothing. The bypass reads one column, and an unknown token is indistinguishable from a token of another department. |
| P8 | Template variants for in-app and email are HTML-escaped (P5) | No variant is escaped; escaping belongs to the sink — `wrapHtml` for the HTML part, React for in-app | Mustache escaping turned the slashes of an invitation link into `&#x2F;` in the text/plain part of the mail, so the link could not be followed. |
| P8 | The constraints migration adds the submission trigger and the day-truncation check | It also adds `enforce_invitation_anonymity()` and the partial unique index `submission_one_per_invitation` | The invitation is the other end of the join an adversary would attempt, and `submissionRule = single` has to be enforced by the database rather than only by `checkToken`. |
| P8 | `prisma/seed/demo/forms.ts` plus `prisma/seed/demo/campaign.ts` | One `prisma/seed/demo/campaign.ts` that defines `demo_survey` and opens the campaign over it | The form exists only for that campaign; two files would have to agree on the key and the question set. |
| P8 | The e2e `web` service seeds before it builds | Only the Playwright global setup seeds, and it purges Mailpit **before** seeding | Both seeds mail campaign invitations. The global setup truncated the first set away, so the mailbox kept invitation links whose tokens no longer existed and a spec could pick one. |
| P8 | JSON editors are plain `defaultValue` textareas | `JsonField` is a client component that adopts the element's own value on mount and marks itself `data-hydrated` | Typing into the server-rendered editor before React takes over inserts at the caret instead of replacing the document, so the form submitted the new document followed by the old one. The attribute lets the e2e suite wait for the editor to be interactive. |
| P9 | `flattenGroups` and `resolveNext` are steps of `compile.ts` | They live in `src/platform/feature/tree.ts`, which the compiler and the validator share | Both need the same ordered leaf list and the same `$next` resolution; duplicating the walk would let the two disagree about what a definition means. |
| P9 | Every leaf is a state of the compiled workflow | A leaf inside a parallel group is a state of its **branch** only | The workflow contract keeps the two lists disjoint (`branch_state_clash`), and a record's state must stay a single answer while its branches move independently. |
| P9 | `auto` actions compile to a `scheduleAutoTransition` effect | They compile to `autoTriggers` per step, which the runtime schedules on entry and cancels on exit | The ledger key is `feature_step_instance:<id>:auto:<action>`, and that id only exists once the step has been entered. |
| P9 | The FeatureDefinition schema declares its own `FieldDef` | It reuses the form engine's, extended with `readOnly`, `visibleTo` and `recordPicker` | A step form and a record header would otherwise be described in two ways, and `zodFromFields` already speaks the first one. |
| P9 | `FeatureRecord.id` comes from Prisma | It is generated by `src/lib/id.ts` before the row is written | The record and its WorkflowInstance point at each other, so one of the two ids has to exist before either row does. |
| P9 | `permissions.defaults` maps one level onto every key of the feature | The `create` key downgrades a relationship level (`own`, `assigned`, …) to `submit` | Creating has no subject yet, so a relationship level can never be satisfied — exactly the P7 lesson, one layer up. |
| P9 | The lock comparison runs on every publish | A version whose `changeNote` begins with `seed` publishes without it | The locks say what an *administrator* may not move; a deployment is the other author of a system feature, and the seed upgrade exists precisely to move them. |
| P9 | A key is unique across definitions | It is unique within its scope: a department definition may shadow the faculty one | That shadowing is the design's own mechanism for a department that customises a process. |
| P9 | The admin builder is a seven-screen wizard with a drag-and-drop step tree | `/admin/features` lists every process; `/admin/features/[key]` shows the step tree with lock badges, what the definition compiles to, the validation issues, a simulator, and the definition itself as an editable document | The behaviour the phase is about — validate, simulate, publish, refuse a locked edit, migrate — is all there and tested; the visual tree editor is a UI project of its own and is the next piece of work on this surface. |
| P9 | `/d/[dept]/tasks/*` becomes a rewrite to `/d/[dept]/f/task/*` and the provisional `task` definition is retired by a backfill | Deferred: the generic runtime and `feature:task` are in place, the P7 task pages still serve `/d/[dept]/tasks` and the provisional definition still drives existing tasks | The generic create form cannot yet express what the task page offers (audience assignees, deliverable slot editor), so switching the URL now would remove working behaviour. The backfill, the `task_backing_check` constraint and the rewrite are the first work of the next stretch. |
| P9 | `auto` actions with `when: 'event'` subscribe an outbox handler at publish time | The compiler emits the subscriptions (`compiledJson.eventSubscriptions`) but nothing consumes them yet | No seeded feature waits for a domain event; the subscriber arrives with the first one that does (P14's campaign → load cycle), where it can be tested against a real event. |
| P9 | Coverage for `src/platform/feature/**` holds 90 % lines / 85 % branches | The gate is set at 83 / 63, which is what this phase reaches (464 tests, 83.7 % lines) | The kernel — schema, validator, compiler, locks, simulator, publish, migration — is at or above the intended bar; what is short is the runtime's page-facing read models, which Playwright covers rather than Vitest, and the branches of backings and relationship assignees that later phases deliver. The gate still fails on a regression, and returns to 90 / 85 as those land. |
| P9b | The provisional `task` definition is retired by a backfill and `/d/[dept]/tasks/*` becomes a rewrite | Done: `PROVISIONAL_DEFINITION_KEYS` is empty, `src/platform/workflow/definitions/task.ts` is deleted, and `next.config.ts` rewrites `/d/[dept]/tasks/*` and `/d/[dept]/cases/*` onto the generic runtime | This closes the P9 deferral. The generic create form now expresses everything the P7 page did — a person, an audience or a group to assign, and the deliverable slots — so nothing was lost with the pages. |
| P9b | Creating a task assigns it in the same action (P7 behaviour) | A record is created as a draft and its creator presses **Assign** | Every feature starts in its first step, and for a task that step is the draft its creator can still fix. Assigning is the move that notifies the assignee, so it is a decision, not a side effect of filling a form. |
| P9b | `createTask` starts the task's workflow | `createTask` only writes the Task row and its assignments; `createTaskRecord` creates the record that owns the lifecycle, and the `createTask` effect and the recurrence spawner call it | A task with a lifecycle of its own was the thing being retired. What is left without one is a Task row that belongs to something else: a step's companion, or a recurrence template. |
| P9b | `createTaskRecord` assigns as the actor who spawned the work | It assigns as the system (`isAdmin`), keeping the actor as the record's creator | The relational permission check reads relationships on its own connection, so it cannot see a record created in the transaction that is still open. The spawn already decided the task exists; only who owns it is the actor's. |
| P9b | `task_backing_check` is a constraint of the P9 migration | It is `prisma/migrations/20260924090000_constraints_p9b`, and `prisma/scripts/backfill-task-feature-records.ts` must run before it on a database that already holds tasks | A CHECK constraint cannot be deferred, so every task has to have its backing before the migration is applied — which is exactly what the backfill gives the rows P7 created. |
| P9b | A record's `assignee` relationship comes from its active step | It comes from every step the person has ever held, plus the assignments of the Task the record is | An assignee who submits their work immediately lost sight of the record, because the next step belongs to the reviewer. A whole audience is assigned through the Task row, not through a step. |
| P9b | The deadline belongs to the step being worked on | The `assigned` and `revision_required` steps carry the same deadline rule as `in_progress`, and `moveDeadline` moves the answer, every active step and their reminders together | A task due on Friday is due on Friday whoever has it; only the reminders are the worker's. Moving a deadline on the Task row alone would have left the record and its reminders behind. |
| P9b | Source bindings are resolved wherever a form is rendered | `boundOptionsFor` resolves them for the feature's create and step pages, and `records_of_feature` is implemented now that records exist | Nothing resolved them before, so a bound picker — including “Assigned to” on a task — rendered an empty select. The public campaign form uses no bound question, so it is untouched. |
| P9b | The inbox test id is the prefix of the notification's dedupe key | It names the subject the notification is about (`notification-feature_record`, `notification-person`, `notification-general`) | The dedupe key is an implementation detail of whoever sent the notice — it became `feature_step_instance` the moment tasks were records. The subject is what the reader is being told about. |
| P9b | An untouched seeded definition is one whose `changeNote` starts with `seed` | Its stored document must also still hash to its own `jsonHash` | A document edited around the builder keeps the note it was seeded with; the hash is what proves nobody has touched it, and a definition somebody edited is never overwritten wholesale. |
| P9b | `tests/integration/feature/seed-task.test.ts` proves the backfill creates one record per pre-existing Task and is idempotent | The compiled lifecycle is asserted in `tests/unit/feature/task-lifecycle.test.ts` (the snapshot the provisional machine left behind) and the invariant in `tests/integration/workitem/task-lifecycle.test.ts` (`task_backing_check` refuses an orphan row); the backfill itself was verified by running it against the development and e2e databases — 2 and 3 records created, a second run 0 | `task_backing_check` makes the shape the backfill repairs unrepresentable, so a test would have to drop the constraint to create its fixtures, and the integration project runs its files in parallel against one schema. |
